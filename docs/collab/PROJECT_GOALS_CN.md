## 0. 我对项目目标的理解

在固定摄像机拍摄的作业视频中，以单人作业为主、偶有他人入镜、未来最多 10 人，逐帧估计作业者正在看画面中的哪个位置。系统输出可审计的逐帧记录（头部观测、视线 heatmap 与峰值、视线是否在画面内），供下游 Multi-Pose 的作业与行为分析使用，同时生成渲染视频用于人工检查和演示。

依据：07-21 设计写明“默认为一名作业者优化，契约支持最多十人”；交接快照写明“重点使用场景是单人作业”；中文 README 规划以第三方库方式接入 Multi-Pose；你的真实素材是 4K 与 1080p 的作业视频，并已制作过演示视频。第 4 节列出需要你确认的细节。

**关键发现：保守门控筛掉的恰好是视线落在画面内的帧。** 7 月 23 日的运行还没有门控，Gazelle 对每个头都做了推理，可以直接比较：

| 头部观测类型（未门控运行） | sample1 中 in/out ≥ 0.5 的比例 | sample2 中 in/out ≥ 0.5 的比例 |
| --- | --- | --- |
| Face Landmarker 成功：保守模式会放行 | 25.5% | 6.6% |
| Face Landmarker 失败：保守模式会拒绝 | 89.6% | 72.8% |
| 仅姿态：保守模式会拒绝 | 49.0% | 78.3% |

同一帧、同一头框在两个版本中给出完全相同的分数，说明这不是模型回归，而是门控的筛选效应。合理的解释是：作业者面向摄像机时人脸 landmark 最容易成功，而此时视线多半朝向摄像机方向，目标在画面外；低头看工作台时 landmark 常常失败，而视线目标正好在画面内。这一点是推断，需要标注数据确认（见 F2）。

## 3. 发现的错误与疏漏

### 3.1 目标与方法层面（影响研究结论）

- **F1 保守门控的前提与 Gazelle 的能力不符。** 门控要求 Face Landmarker 成功并给出头姿，才允许 Gazelle 推理。但 Gazelle 只需要场景图像和头框，训练数据包含背面与侧面头部。在你的视频上，门控保留了约四分之一的帧，且多为视线在画面外的帧。建议见决策 D10。
- **F2 没有目标场景的标注数据与量化验收。** 至今的质量判断都来自看渲染视频；531 个测试只验证软件契约，不验证视线是否正确。没有标注，就无法判断保守模式与诊断模式哪个更对、任何改进是否真的有效。建议见决策 D12。
- **F3 所有阈值都未经领域标定。** in/out 阈值 0.5、人脸质量 0.50、跟踪激活 0.50 都来自上游默认或设计初值。
- **F4 单人模式没有定义“主体是谁”。** 画面出现第二个人时，系统没有规则决定跟哪一个人，于是出现跨人融合（GZ-01）和 ID 频繁更换（sample2 有 525 个 ID）。D1 解决选择规则；主体身份长期稳定见决策 D11。
- **F5 与 Multi-Pose 的分工没有定论。** 中文 README 写的是由 Multi-Pose 负责人物跟踪和头框，而本仓库已自建 MediaPipe 加 ByteTrack 的完整感知链。两种集成方式的接口完全不同，需要在第 3 阶段之前决定（问题 Q5）。

### 3.2 既往开发中的实现缺陷

详见分析报告。最重要的 8 组：单人模式跨人误配（GZ-01）、面部参考射线上下反向（GZ-02）、每条轨迹首帧丢失（GZ-03）、`--overwrite` 先删后验（GZ-04）、子格头框退化（GZ-05）、打包不可用（GZ-06）、时间戳时钟（GZ-07）、研究脚本在 Windows 不可用（GZ-08）。

### 3.3 流程与工程管理

- **P1 PR 堆叠链从未合并。** PR #2、#3、#4、#5 逐层堆叠，自 6 月起都未合并，`main` 比 PR #5 落后 65 个提交。新的阶段分支会成为第 5 层。建议阶段 2 验收后决定合并方式（决策 P-merge）。
- **P2 验收依赖手动敲命令。** 建议增加一个本地验收脚本，你在独立目录一键运行离线门与可选真实 smoke，生成统一格式的结果（TASK-008）。
- **P3 `--output-dir` 被当作输出文件名用过。** sample1 的 `run_config.json` 记录了 `--output-dir samples\sample_rander.mp4`。它其实是输出根目录。建议 CLI 拒绝带媒体后缀的输出目录，并在文档中强调（TASK-008）。
- **P4 输入与多次输出混放。** 你的验收目录 `samples/` 同时放了原始视频与多轮结果；`sample/` 目录不在 `.gitignore` 中，存在误提交的风险。建议输出统一放到仓库外的结果根目录，并按日期与配置命名。
- **P5 输出不记录代码版本。** `run_config.json` 不包含提交 SHA 与关键依赖版本，07-21 设计 §16 的这项要求也未实现。跨版本对比结果时无法追溯（TASK-008）。
