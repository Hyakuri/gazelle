## 1. 结论

1. **MediaPipe 1.1.1 可以稳定运行，但对本项目没有精度或速度提升。**
   - 1.0.0 至 1.1.1 的更新集中在构建系统、LiteRT 加速后端和 Python 3.13/3.14 支持上，人脸与姿态模型没有更新。
   - 感知状态、头框、人脸框、关键点与 landmarks 逐项相同。面部变换矩阵、头部姿态角与人脸参考射线只有浮点级差异，其中头部姿态角最多相差 0.0016°。
   - MediaPipe 耗时持平到略慢：两种运行顺序下候选环境都稍慢，合计 +3% 与 +12%，与运行间波动同量级。
   - Windows 上仍不能用 GPU，已实测：GPU 委托初始化失败，报 `built without GPU support`。
2. **候选环境已建好，并通过全部检查。** 包括离线门 562 项、真实 GPU 运行、视频读取逐帧比对、渲染与 H.264 封装。Gazelle 的输出与现用环境等价（in/out 最大差 0.001，热图峰值完全一致）。
3. **新环境不改变精度，速度视输入而定，总体没有速度收益。**
   - 4K 管线实测：Gazelle 每次调用的中位耗时从 81 ms 变成 96 至 102 ms，慢约 20%。原因是 CPU 上的整帧内存拷贝变慢。
   - 1080p 只做了探针测量：候选环境每次调用 29 ms，现用环境 33 ms。
4. **更大的效率空间在代码，与环境无关。**
   - Gazelle 的输入预处理（整帧转张量、归一化、缩放）目前在 CPU 上做。按相同的运算顺序改在 GPU 上做，输出等价：in/out 最大差 1.8e-4，峰值逐帧一致。
   - 在候选环境的完整管线中实测（4K，300 帧），每次调用的中位耗时：

     | 头部来源 | 现有做法 | GPU 预处理 |
     | --- | --- | --- |
     | 静态头框 | 98.9 ms | 41.1 ms（可写复制）；35.8 ms（只读数组） |
     | MediaPipe | 95.6 ms | 47.9 ms |

5. **决定与安排**（见 §0）：仓库侧切换为第 2 轮第一项（TASK-137）；TASK-136 在第 3 轮开头实施。切换的理由主要是保持依赖更新，而不是精度或速度：Python 3.11 的安全支持到 2027-10 结束，numpy 2.5、scipy 1.18 等新版本已不再支持 3.11。

### 3.2 xFormers 的处理

- PyPI 上最新的 xformers 0.0.35 Windows 包不含 CUDA 算子，调用时报 `No operator found for memory_efficient_attention_forward`。
- PyTorch cu130 源中的 0.0.34 可以运行，但元数据要求 `torch==2.10.0`，与 torch 2.14.1 不配套。
- 没有 xFormers 时，DINOv2 改用 PyTorch 自带的 `scaled_dot_product_attention`。实测前向耗时 16.0 对 16.2 ms，输出逐项相同。
- 因此候选环境不安装 xFormers。仓库中 xFormers/Triton 的回退逻辑不需要改动，也没有安装 Triton。

## 5. 速度分析

### 5.1 管线中的 Gazelle 调用耗时（`inference_ms`，中位，跳过第一次调用）

| 运行 | 现用环境 | 候选环境 |
| --- | --- | --- |
| 静态头框，300 次调用 | 80.6 ms | 101.8（xFormers 开）、100.0（关）、96.0、98.9（最终配置） |
| MediaPipe 头部，73 次调用 | 92.3、89.5 ms | 101.4、103.0（关 xFormers）、95.2、91.3、95.6 ms |
| MediaPipe 头部并渲染，73 次调用 | 93.0（mp4v）、86.8（avc1） | 86.8（mp4v）、88.8（avc1） |

静态头框下候选环境稳定地慢 19% 至 26%；MediaPipe 头部下差异较小，并且与运行间波动重叠。

### 5.2 分阶段计时（4K numpy 帧，60 帧，交替运行两轮）

| 阶段 | 现用环境 | 候选环境 |
| --- | --- | --- |
| numpy 帧转 PIL 图像 | 33.3、36.7 ms | 48.3、50.8 ms |
| ToTensor | 27.5、32.4 | 41.3、42.0 |
| Normalize | 9.6、10.3 | 9.7、9.8 |
| Resize | 3.5、3.7 | 3.3、3.3 |
| 拷贝到 GPU | 0.5 | 0.5 |
| 模型前向 | 33.0、31.6 | 33.0、33.0 |
| `predict_frame` 合计 | 108.6、108.9 | 137.7、139.7 |

管线中，读取器已经先把 numpy 帧转成 PIL 图像，这一步不计入 `inference_ms`。预测器内部仍会对 PIL 图像再做一次同模式的 `convert("RGB")` 整帧复制，约 7 ms，这部分计入 `inference_ms`。

变慢的都是单线程的大块内存拷贝：numpy 的 clip 与类型转换、Pillow 的 fromarray 与 convert、PIL 转 numpy。多线程的 PyTorch 运算没有变慢。把进程限定在不同的核上重测：

| 绑定 | 现用环境（PIL 部分 / 张量部分） | 候选环境 |
| --- | --- | --- |
| 不绑定（两轮） | 27.8、28.4 / 27.9、28.8 ms | 43.8、35.9 / 38.0、35.1 ms |
| 只用性能核 | 23.0 / 25.9 | 26.7 / 29.5 |
| 只用能效核 | 39.7 / 42.3 | 38.3 / 39.9 |

可见差异有两个来源：

- 候选环境在性能核上本身慢约 15%（实测）。
- 不绑定时，候选环境的数字更接近能效核的数字，说明主线程更常被调度到能效核上（推断，没有直接记录调度）。

Windows 10 对混合架构 CPU 的调度较弱，这类波动会一直存在。预处理移到 GPU 后，这部分差异会大幅缩小。

### 5.3 优化探针（单独脚本，60 帧，每帧连续运行多次前向）

**A. 管线实际的输入（PIL 图像）：现有做法对 GPU 预处理**

| 输入 | 环境 | 现有做法 | GPU 预处理 | 热图最大差 | in/out 最大差 | 峰值一致 |
| --- | --- | --- | --- | --- | --- | --- |
| 4K | 现用 | 69.2（预处理 46.9，前向 22.7） | 37.0（15.4，20.3） | ≤ 1.8e-4 | ≤ 5.4e-5 | 60/60 |
| 4K | 候选 | 82.8（66.7，16.1） | 40.8（23.9，17.6） | ≤ 2.2e-4 | ≤ 1.5e-4 | 60/60 |
| 1080p | 现用 | 33.3（10.6，22.9） | 23.6（3.4，20.0） | ≤ 1.7e-4 | ≤ 4.0e-5 | 60/60 |
| 1080p | 候选 | 28.8（11.8，16.1） | 21.2（4.9，15.9） | ≤ 2.3e-4 | ≤ 1.3e-4 | 60/60 |

说明：

- 合计是逐帧“预处理 + 前向”的中位数，所以与两项各自中位数之和略有出入。
- 这组 GPU 预处理用的是只读的 `np.asarray`，PyTorch 会对此发出一次 warning。正式实现需要处理这一点，见 TASK-136。
- GPU 预处理的运算顺序与现有完全相同：÷255、Normalize、带抗锯齿的 Resize。差异只来自浮点运算顺序，可视为等价。
- 若输入直接是 numpy 数组，可以省去 PIL 转 numpy 这一步：4K 现有做法为 102.3 与 112.4 ms，GPU 预处理后为 28.4 与 23.7 ms。

**B. 精度选项（在 GPU 预处理的基础上；差异相对于现有 FP32 做法）**

| 输入 | 选项 | 现用环境前向 | 候选环境前向 | 热图最大差 | in/out 最大差 | 峰值一致 |
| --- | --- | --- | --- | --- | --- | --- |
| 4K | FP32（基准） | 22.4 | 16.2 | ≤ 2.2e-4 | ≤ 1.5e-4 | 60/60 |
| 4K | TF32 | 17.0 | 12.5 | ≤ 1.3e-3 | ≤ 2.2e-3 | 60/60 |
| 4K | bf16 | 13.1 | 11.7 | ≤ 0.045 | ≤ 0.031 | 55/60、56/60，峰值最大偏移 0.08 |
| 1080p | TF32 | 17.8 | 14.0 | ≤ 7.8e-4 | ≤ 1.2e-3 | 60/60 |
| 1080p | bf16 | 13.5 | 12.6 | ≤ 0.050 | ≤ 0.041 | 58/60、55/60 |

说明：

- 候选环境这一列是在仍装有 xFormers 时测的。最终配置（不装 xFormers）的 4K 前向为 FP32 16.0、TF32 13.0、bf16 9.9 ms，差异数字相同。
- 1080p 输入由 4K 帧用 `INTER_AREA` 缩小得到，模拟阶段 3 的同步代理视频。
- 前向耗时与 §5.2 不同（约 33 ms 对 16 至 23 ms），原因没有查明。§5.3 的前向紧接在 47 至 108 ms 的纯 CPU 处理之后，仍然很快，所以并不是简单的 GPU 空闲降频。实际效果以 §5.4 的管线实测为准。
- TF32 每次调用再快 2 至 5 ms，数值差异约 1e-3。收益小，而且会改变数值，暂不采用；可以在阶段 3 的消融中作为可选项。
- bf16 会让少数帧的峰值移动，不采用。

### 5.4 管线级实测：GPU 预处理（候选环境，4K，300 帧）

做法：在仓库外的探针中替换预测器的预处理，运行完整的 `main.py`，其余代码不变（`pipeline_patch_probe.py`）。三组对照在同一时段连续运行。

| 头部来源 | 运行 | `inference_ms` 中位 | p90 | 与基准相比 |
| --- | --- | --- | --- | --- |
| 静态头框 | 基准（现有做法） | 98.9 ms | 112.9 | — |
| 静态头框 | GPU 预处理，可写复制 `np.array` | 41.1 | 43.8 | −58%；in/out 最大差 1.8e-4，峰值与状态 300/300 一致 |
| 静态头框 | GPU 预处理，只读 `np.asarray`，局部忽略该 warning | 35.8 | 38.5 | −64%；输出同上 |
